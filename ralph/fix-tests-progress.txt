### Fix 10: Happy-DOM locator scoped role queries missing implicit ARIA roles and accessible name filtering (2026-01-18)
**Tests fixed:** Multiple tests including `strength-workflows.spec.ts` (3 tests) and `bodyweight-exercise.spec.ts` (2 tests)

**Issue 1 - Missing implicit ARIA roles:** The scoped `getByRole()` in Happy-DOM locator used a simple CSS selector that only matched explicit role attributes:
```ts
const els = parentEl.querySelectorAll<HTMLElement>(`[role="${role}"], ${role}`)
```
This failed to match HTML elements with implicit ARIA roles (e.g., `<td>` has implicit role `cell`, `<tr>` has implicit role `row`). This caused "No active set row found" errors when tests tried to find cells within table rows.

**Issue 2 - Missing accessible name filtering:** The scoped role query didn't filter by the `name` option, causing "Multiple elements found" errors when trying to find specific inputs by aria-label.

**Fix 1 - Added implicit ARIA role mapping:**
```ts
const IMPLICIT_ROLE_SELECTORS: Record<string, string> = {
  table: 'table',
  row: 'tr',
  cell: 'td',
  columnheader: 'th',
  button: 'button, input[type="button"], ...',
  textbox: 'input:not([type]), input[type="text"], ...',
  spinbutton: 'input[type="number"]',
  // ... more mappings
}

function buildRoleSelector(role: string): string {
  const explicitSelector = `[role="${role}"]`
  const implicitSelector = IMPLICIT_ROLE_SELECTORS[role]
  if (implicitSelector) {
    return `${explicitSelector}, ${implicitSelector}`
  }
  return explicitSelector
}
```

**Fix 2 - Added accessible name filtering:**
```ts
function getAccessibleName(element: HTMLElement): string {
  // Checks aria-label, aria-labelledby, associated label, and text content
}

function filterByAccessibleName(elements, namePattern) {
  // Filters elements by their accessible name matching the pattern
}
```

**Fix 3 - Updated strength-workflows.spec.ts to use correct APIs:**
Changed from browser-only APIs to abstraction layer:

### Fix 17: Happy-DOM getByRole('textbox') matching elements with explicit role="spinbutton" (2026-01-18)
**Test fixed:** `dialog is keyboard-free (no text inputs)` in `edit-exercise-dialog.spec.ts`

**Issue:** The scoped `getByRole('textbox')` query in Happy-DOM was incorrectly matching `<input type="text" role="spinbutton">` elements. The `NumberFieldInput` component from `reka-ui` renders an `<input type="text">` with explicit `role="spinbutton"`. The Happy-DOM locator's implicit role mapping was matching `input[type="text"]` for the `textbox` role, ignoring the explicit `role="spinbutton"` attribute:

```ts
textbox: 'input:not([type]), input[type="text"], ...',
```

This caused the test to find 2 textboxes (the target reps and set count spinbuttons) instead of 0, failing the assertion:
```
AssertionError: expected 2 to be +0
```

**Fix:** Added a `filterByExplicitRole()` function in `src/__tests__/helpers/locator/happy-dom.ts` that excludes elements with explicit role attributes that differ from the target role:

```ts
function filterByExplicitRole(elements: Array<HTMLElement>, targetRole: string): Array<HTMLElement> {
  return elements.filter((el) => {
    const explicitRole = el.getAttribute('role')
    // If no explicit role, the implicit role applies - keep the element
    if (!explicitRole) return true
    // If explicit role matches target, keep it
    if (explicitRole === targetRole) return true
    // Explicit role differs from target - exclude this element
    return false
  })
}
```

This is applied in `createScopedRoleQuery()` before the accessible name filter.

### Fix 19: benchmark-variable-reps.spec.ts "copied round has identical exercises and reps" test (2026-01-18)
**Test fixed:** `copied round has identical exercises and reps` in `benchmark-variable-reps.spec.ts`

**Issue:** The test used `expectElement(page.getByText('Burpees')).toBeVisible()` after copying a round, which inconsistently failed in Happy-DOM mode. The `page.getByText()` locator relies on `screen.queryAllByText()` from testing-library, which sometimes returned empty results even though the element was present in the DOM (verified via synchronous `query()` calls).

The root cause appears to be a timing issue between Vue's reactivity updates and testing-library's `waitFor` polling mechanism. When the round is copied and the new round is selected:
1. `currentExercises` computed recalculates
2. Vue schedules a render
3. The `BenchmarkExerciseList` component receives new props
4. The component's watch updates `exercisesList` (fires on next tick due to default `flush: 'pre'`)
5. During this brief window, `queryAllByText` might query before the DOM is fully updated

**Fix:** Changed the test assertions to use `getByTestId` (which is more reliable in Happy-DOM) instead of `getByText`, and then verify content using `toHaveTextContent`:

```ts
// Before (unreliable in Happy-DOM):
await expectElement(page.getByText('Burpees')).toBeVisible()
await expectElement(page.getByText('40')).toBeVisible()

// After (reliable):
const exerciseItem = page.getByTestId('benchmark-exercise-item')
await expectElement(exerciseItem).toBeVisible()
await expectElement(exerciseItem).toHaveTextContent(/Burpees/i)
await expectElement(exerciseItem).toHaveTextContent(/40/)
```
