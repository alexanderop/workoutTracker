Repositories

Persistence layer - type-safe database access via well-defined interfaces. Repositories abstract IndexedDB complexity.

📦 What Repositories Manage

Repositories are the only layer that talks to the database:

  • 💾 CRUD operations - Create, read, update, delete
  • 🔍 Queries - Search, filter, date ranges
  • 🔄 Type conversions - Domain types ↔ DB types
  • 🎯 Data integrity - Validation, constraints

🔒 Golden Rule: Components never call repositories directly. Always go through stores or composables.

🏗️ Repository Architecture

Three Layers

1. Public API (src/db/index.ts)

  • Singleton getters for each repository
  • getSettingsRepository(), getExercisesRepository(), etc.
  • Example: lines 19-45

2. Interfaces (src/db/interfaces.ts)

  • Type-safe contracts for each repository
  • Function overloading for type safety
  • Example: SettingsRepository (lines 31-84)

3. Implementations (src/db/implementations/dexie/*.ts)

  • Concrete Dexie implementations
  • Actual IndexedDB operations
  • Type converters integration

🔄 Type Conversions

Location: src/db/converters.ts

Why needed?

  • Database types use null for "no value" (IndexedDB doesn't support undefined)
  • Domain types use undefined for optional values (TypeScript best practice)

// Set conversions (lines 41-60)
setToDb(set: Set): DbSet {
  return {
    id: String(set.id),
    kg: set.kg,
    reps: set.reps,
    rir: set.rir,
    status: set.status,
    completedAt: set.status === 'completed' ? Date.now() : null
  }
}

Pattern: Always convert at repository boundaries

🎯 Repository Patterns

1. Singleton Access Pattern

Always use getter functions, never instantiate directly.

// ✅ CORRECT
const repo = getCustomExercisesRepository()
await repo.add(exercise)

// ❌ WRONG - Never do this
import { customExercisesRepo } from '...'

2. Interface-Based Design

Code against interfaces, not implementations.

// Repository interface defines contract
type CustomExercisesRepository = {
  getAll(): Promise<ReadonlyArray<DbCustomExercise>>
  add(exercise: Readonly<DbCustomExercise>): Promise<void>
}

// Implementation details hidden
function getCustomExercisesRepository(): CustomExercisesRepository {
  return dexieCustomExercisesRepository
}

Benefit: Easy to swap implementations (e.g., for testing)

3. Type-Safe Overloading

Use function overloads for different return types.

// Settings repository (lines 23-63)
async function get(key: 'theme'): Promise<'light' | 'dark' | 'system'>
async function get(key: 'weightUnit'): Promise<'kg' | 'lbs'>
async function get(key: 'language'): Promise<'en' | 'de' | undefined>
async function get(key: UserSettingKey) {
  const setting = await db.settings.get(key)
  if (!setting) return SETTING_DEFAULTS[key]

  // Type narrowing via switch
  switch (setting.key) {
    case 'theme': return setting.value
    case 'weightUnit': return setting.value
    // ...
  }
}

Benefit: TypeScript knows exact return type for each key

✅ Use Repositories When...

  • ✅ You need database access (reads or writes)
  • ✅ Called from stores or composables only
  • ✅ Converting between domain and DB types

❌ Don't Use Repositories When...

  • ❌ Called directly from components (use stores/composables instead)
  • ❌ You just need cached data (read from stores)
  • ❌ You need business logic (use composables)

🔗 Integration with Other Layers

Stores → Repositories:

  • Stores call repositories for initial load and updates
  • Example: exercisesStore.loadFromDb() calls getCustomExercisesRepository().getAll()

Composables → Repositories:

  • Composables call repositories directly for per-component data
  • Example: useWorkoutsList calls getWorkoutsRepository().getHistory()

Components → Repositories:

  • ❌ NEVER - Components should never call repositories directly
  • ✅ Use stores or composables as intermediaries
