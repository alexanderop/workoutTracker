Decision Tree

Quick guide to help you decide: Should I use a Store, Composable, or Repository?

🎯 Quick Checklists

Use Local Component State When...

  • ✅ State is only used in one component
  • ✅ State is temporary (form inputs, UI toggles)
  • ✅ No persistence needed
  • ✅ Not reused anywhere else

Example:

const isDialogOpen = ref(false)
const searchQuery = ref('')
const selectedTab = ref('overview')

Use a Composable When...

  • ✅ Logic is reusable across components
  • ✅ State is temporary or component-specific
  • ✅ You need business logic (validation, formatting, coordination)
  • ✅ Bridging between stores and repositories
  • ✅ Managing derived/computed state
  • ✅ State machines (timers, workflows)

Examples:

  • useWorkoutsList() - Fetch from repos, cache temporarily
  • useExerciseSearch() - Filter store data reactively
  • useWorkoutPersistence() - Auto-save coordination
  • useBaseTimer() - State machine logic

Use a Pinia Store When...

  • ✅ Data is accessed frequently across many components
  • ✅ Data is loaded once and rarely changes
  • ✅ You need synchronous access (no awaits in components)
  • ✅ Data represents domain-level state (exercises, settings)
  • ✅ Data is global app state

Examples:

  • exercisesStore - Exercise library cache
  • settingsStore - User preferences cache

Call a Repository When...

  • ✅ You're in a store or composable (never from components)
  • ✅ You need database access (read or write)
  • ✅ Converting between domain and DB types

Examples:

  • getCustomExercisesRepository().add() - From store
  • getWorkoutsRepository().getHistory() - From composable

🚨 Common Mistakes

❌ NEVER: Component → Repository

Wrong:

// Component.vue
const exercises = await getCustomExercisesRepository().getAll()

Right:

// Component.vue
const store = useExercisesStore()
const exercises = store.getAllExercises() // Synchronous from cache

❌ NEVER: Store data that changes frequently

Wrong:

// Creating a store for active workout state
const activeWorkoutStore = defineStore('activeWorkout', ...)

Right:

// Use singleton ref for temporary state
const workoutRef = ref<Workout>(...)
export function getWorkoutRef() { return workoutRef }

❌ NEVER: Duplicate logic across components

Wrong:

// ComponentA.vue
const filtered = computed(() => exercises.value.filter(...))

// ComponentB.vue
const filtered = computed(() => exercises.value.filter(...))

Right:

// composables/useExerciseSearch.ts
export function useExerciseSearch() {
  const filtered = computed(() => ...)
  return { filtered }
}

// Both components use it
const { filtered } = useExerciseSearch()

📊 Real Examples from Codebase

Scenario 1: Exercise Library

Question: Where should I store custom exercises?

Analysis:

  • ✅ Accessed frequently (exercise picker, workout builder)
  • ✅ Loaded once at startup
  • ✅ Global app state
  • ✅ Needs to be synchronous

Decision: Pinia Store (src/stores/exercises.ts)

Scenario 2: Workout History

Question: Where should I load completed workouts?

Analysis:

  • ❌ Only used in history view (not global)
  • ❌ Large dataset (don't want to cache all)
  • ✅ Needs pagination, filtering
  • ✅ Loaded per-component

Decision: Composable (src/composables/useWorkoutsList.ts)

Scenario 3: Exercise Search

Question: Where should I implement search/filter logic?

Analysis:

  • ✅ Reusable across components
  • ✅ Derives state from store data
  • ✅ Reactive computed filtering
  • ❌ Not stored in DB (temporary)

Decision: Composable (src/composables/useExerciseSearch.ts)

Scenario 4: Auto-Save Workout

Question: How should I auto-save the active workout?

Analysis:

  • ✅ Needs to watch state changes
  • ✅ Debounce to avoid excessive writes
  • ✅ Coordinate memory ↔ DB
  • ✅ Type conversions needed

Decision: Composable (src/features/workout/composables/useWorkoutPersistence.ts)

Scenario 5: Timer State

Question: Where should I manage rest timer state?

Analysis:

  • ✅ State machine (idle → running → paused)
  • ✅ Reusable (rest, AMRAP, EMOM, Tabata)
  • ❌ No persistence needed
  • ❌ Component-specific

Decision: Composable (src/composables/timers/useBaseTimer.ts)

🧠 Mental Model

Ask yourself these questions in order:

1. Does it need to persist to database?

  • No → Local state or composable
  • Yes → Continue...

2. Where am I calling from?

  • Component → Use store or composable (never repository)
  • Store/Composable → Can call repository

3. Is it accessed frequently across many components?

  • Yes + Global → Pinia Store
  • No + Per-component → Composable

4. Is the logic reusable?

  • Yes → Composable
  • No → Local component state
