📖 Example 1: App Initialization

Scenario: Load stores when the app starts

Location: src/composables/useAppInitialization.ts:35-77

Flow:

async function initialize(): Promise<void> {
  // 1. Seed popular exercises (idempotent)
  await seedPopularExercises()

  // 2. Load stores in parallel (caches from DB)
  await Promise.all([
    settingsStore.loadFromDb(),      // Repository → Store cache
    exercisesStore.loadFromDb()      // Repository → Store cache
  ])

  // 3. Check for active workout (from repository)
  const activeWorkout = await getActiveWorkoutRepository().get()

  // 4. If exists, prompt to resume
  if (activeWorkout && activeWorkout.blocks.length > 0) {
    initState.value = {
      status: 'prompt-resume',
      workoutName: activeWorkout.name,
      blockCount: activeWorkout.blocks.length
    }
  }
}

Key Insights:

  • Stores are loaded in parallel for speed
  • After loading, all store access is synchronous
  • Active workout check uses repository directly (not cached)

📖 Example 2: Adding an Exercise

Scenario: User creates a custom exercise

Location: src/stores/exercises.ts:33-45

Flow:

async function addExercise(exercise: Omit<CustomExercise, 'id'>): Promise<CustomExercise> {
  // 1. Create DB format with ID
  const dbExercise = createDbCustomExercise(exercise)

  // 2. Save to database FIRST (persistent)
  await getCustomExercisesRepository().add(dbExercise)

  // 3. Convert back to domain type
  const newExercise = dbToCustomExercise(dbExercise)

  // 4. Update local store state
  customExercises.value = [...customExercises.value, newExercise]

  return newExercise
}

Key Insights:

  • DB-first pattern: Always persist before updating cache
  • Type conversions: Domain → DB → Domain
  • Immutable updates: Spread operator creates new array
  • If DB write fails, cache is not updated

📖 Example 3: Searching Exercises

Scenario: User searches for exercises by name

Location: src/composables/useExerciseSearch.ts:73-100

Flow:

export function useExerciseSearch(options?: UseExerciseSearchOptions) {
  const exercisesStore = useExercisesStore()
  const searchQuery = ref('')

  // Computed property with store data
  const allExercises = computed(() => {
    // Reads cached data from store (no DB call!)
    return [...exercisesStore.customExercises].toSorted(...)
  })

  const filteredExercises = computed(() => {
    // Pure filtering functions on cached data
    let result = allExercises.value
    result = filterByMuscle(result, options?.muscleFilter.value)
    result = filterBySearchQuery(result, searchQuery.value, ['name'])
    return result
  })

  return { searchQuery, filteredExercises, allExercises }
}

Key Insights:

  • No DB calls: All data from store cache
  • Reactive filtering: Computed properties auto-update
  • Pure functions: filterByMuscle, filterBySearchQuery
  • Composable composition: Reusable across components

📖 Example 4: Auto-Save Workout

Scenario: User edits workout, changes auto-save to DB

Location: src/features/workout/composables/useWorkoutPersistence.ts:50-81

Flow:

watchDebounced(
  workout,
  async (newWorkout) => {
    if (isDisposed) return
    if (!isInitialized.value) return

    if (newWorkout.blocks.length === 0) {
      // Clear active workout if empty
      await getActiveWorkoutRepository().clear()
      return
    }

    persistenceState.value = { status: 'saving' }

    // Convert domain type to DB type
    const dbWorkout = workoutToDb(newWorkout, currentWorkoutStartedAt)

    // Save to repository
    const [saveError] = await tryCatch(
      getActiveWorkoutRepository().save(dbWorkout)
    )

    if (saveError) {
      persistenceState.value = { status: 'error', error: saveError }
      return
    }

    hasUnsavedChanges.value = false
    persistenceState.value = { status: 'idle' }
  },
  { debounce: 1000, deep: true }  // Auto-save every 1 second of inactivity
)

Key Insights:

  • Debounced: Waits 1 second after changes stop
  • Deep watch: Tracks nested property changes
  • Type conversion: Domain → DB format
  • Error handling: Uses tryCatch pattern
  • State tracking: persistenceState for UI feedback

🔄 Common Patterns Summary

1. Load-Once Pattern (Stores)

When: App initialization

Flow: DB → Repository → Store → Cache

Result: Synchronous access everywhere after initial load

2. DB-First Update Pattern (Stores)

When: Modifying cached data

Flow: Persist to DB first → Update cache second

Result: Cache never out of sync with DB

3. Reactive Filtering Pattern (Composables)

When: Deriving state from stores

Flow: Store cache → Computed → Reactive results

Result: No DB calls, instant updates

4. Auto-Save Pattern (Composables)

When: Coordinating memory ↔ DB

Flow: Watch changes → Debounce → Convert types → Save to DB

Result: Seamless persistence without user action

⏱️ Timing Considerations

Store Loading:

  • Happens once at app startup
  • Parallel loading for speed
  • Blocks UI until loaded (loading spinner)

Auto-Save Debouncing:

  • 1000ms debounce - Waits for typing to stop
  • Prevents excessive DB writes
  • User sees "saving..." indicator

Reactive Filtering:

  • Instant - No async operations
  • Computed properties update on next tick
  • Feels instantaneous to user

🎯 Best Practices from Examples

  • ✅ Parallel loads: Use Promise.all() for independent operations
  • ✅ Type conversions: Always convert at layer boundaries
  • ✅ Error handling: Use tryCatch pattern, never bare try/catch
  • ✅ Debounce writes: Prevent excessive DB operations
  • ✅ Readonly refs: Prevent accidental mutations from composables
  • ✅ Deep watching: Use { deep: true } for nested objects
  • ✅ Loading states: Track isLoading, persistenceState for UI feedback
