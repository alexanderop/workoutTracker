State Management

Three-layer architecture for managing state in the workout tracker. Each layer has a specific purpose and responsibility.

🏗️ Architecture Overview

The app uses a clean separation of concerns across three layers:

  • 📦 Repositories - Persistence layer (IndexedDB via Dexie)
  • 💾 Stores - Domain-level cache (Pinia)
  • 🧩 Composables - Business logic + temporary state

📚 Quick Guide

When to use each layer?

  • Pinia Store → Frequently-accessed data, loaded once at startup (exercises, settings)
  • Composable → Temporary state, derived data, business logic (search, timers, auto-save)
  • Repository → Database access only (never call directly from components)

💡 Golden Rule: Components never call repositories directly. Always go through stores or composables.

🎯 Key Patterns

1. DB-First Updates

  • Always save to database first, then update store cache
  • Example: src/stores/exercises.ts:39-43

2. Load-Once Pattern

  • Stores load data once at app initialization
  • After that, all access is synchronous from cache
  • Example: src/stores/exercises.ts:18-30

3. Auto-Save Pattern

  • Use watchDebounced for reactive persistence
  • Debounce 1000ms to avoid excessive writes
  • Example: src/features/workout/composables/useWorkoutPersistence.ts:50-81

4. Type Conversions

  • Database types use null for no value
  • Domain types use undefined for optional values
  • Converters bridge between them: src/db/converters.ts
