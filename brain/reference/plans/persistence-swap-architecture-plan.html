TL;DR — the architect's verdict

You are roughly 70% of the way to swappable persistence already. Every repository has a TypeScript interface, Dexie is confined to one folder, and a full mock provider proves the seam works. The remaining work is closing four seam leaks, adding a reactivity port (the one capability the current design lacks and the one sync will demand), and writing a second adapter. Jazz itself is mid-rewrite — target its 2.0 relational model in your interfaces, but don't ship it to production until 2.0 stabilizes.

Seam quality today Strong — interfaces + factory + mock exist

12 repository interfaces, DI'd factories, zero Dexie imports outside src/db.

Dexie Stays the production default

Fast, tiny, proven. It becomes "adapter #1", not legacy code.

Jazz Spike behind a flag, don't adopt yet

2.0 (tables + WHERE queries) is nearly isomorphic to Dexie — but it's alpha, with a WASM/OPFS footprint.

Biggest structural gap No reactive read layer

All reads are one-shot async + manual reload. Sync-capable backends need subscriptions.

What Jazz actually is (July 2026)

The most important research finding: there are two Jazzes. The monorepo you cloned is 2.0.0-alpha.52 — a ground-up rewrite. npm install jazz-tools gives you 0.20.19, a completely different API. The live docs at jazz.tools already describe 2.0, so online documentation and the installable stable package do not match. Any plan must pick a side.

What a 2.0 schema and reactive Vue read look like — note how close this is to a Dexie table + a live query:

// schema — jazz-tools 2.0
import { schema as s } from "jazz-tools";

const schema = {
  workouts: s.table({
    startedAt:   s.timestamp(),
    completedAt: s.timestamp().optional(),
    benchmarkId: s.ref("benchmarks").optional(),
    blocks:      s.json(),          // your DbWorkoutBlock[] union, as-is
    legacyId:    s.string(),        // old Dexie UUID, for migration integrity
  }),
  benchmarks: s.table({ name: s.string(), rounds: s.json(), /* … */ }),
};
export const app = s.defineApp(schema);

// component — reactive, index-backed query
import { useAll, useDb } from "jazz-tools/vue";
const { data: recent } = useAll(
  app.workouts.where({ completedAt: { isNull: false } })
              .orderBy("completedAt", "desc").limit(20)
);
Why this matters for the plan. Jazz 2.0's surface (insert / update / delete / where / orderBy / limit + reactive subscriptions + optional sync URL) is close enough to Dexie's that one repository interface can be implemented faithfully by both. That's the property that makes "swappable" realistic rather than aspirational. Your embedded-blocks document model and client-generated UUIDs already fit; sync becomes a config flag (serverUrl), not a rewrite.

Target architecture

Classic hexagonal: the feature layer talks to ports (repository interfaces + a new reactivity port), and each storage engine is an adapter behind them. Nothing above the seam knows which adapter is live.

↓ one adapter active at runtime, chosen at bootstrap

Dexie adapter — production default

implementations/dexie/ · IndexedDB · ACID transactions · liveQuery() backs the reactivity port

Jazz adapter — spike → future

implementations/jazz/ · OPFS + WASM · CRDT merge · subscriptions back the reactivity port · sync = serverUrl flag

In-memory adapter — tests

Replaces raw-db test access · same interface · deterministic, no fake-indexeddb needed

Rules that keep it swappable

  • The interface is the contract, Dexie is not the spec. Any capability an adapter can't honor (e.g. ACID) must be expressible in the interface's documented semantics, not assumed by callers.
  • Intents over table operations. Repositories keep exposing verbs like completeWorkout(), never "run a transaction over these tables". Atomicity is an adapter implementation detail.
  • Reads through the reactivity port wherever data can change underneath the UI — which after sync ships is everywhere.
  • Adapter chosen once, at bootstrap (env/flag), not per-call. No dual-running in production; dual-write exists only inside the one-time migrator.
04

The five design moves

Move 1 — Complete the provider registry (the actual swap switch)

Today the provider is lazily hardcoded to Dexie. Add injection and fold the stray exerciseProgress singleton into the provider so there is exactly one seam:

// src/db/provider.ts
let provider: RepositoryProvider | null = null;

export function setRepositoryProvider(p: RepositoryProvider): void { provider = p; }
export function getRepositoryProvider(): RepositoryProvider {
  return (provider ??= createDefaultProvider());
}

// src/main.ts — the ONLY place that knows adapters exist
const backend = import.meta.env.VITE_DATA_BACKEND ?? "dexie";
setRepositoryProvider(
  backend === "jazz"
    ? await createJazzRepositoryProvider()
    : createDexieRepositoryProvider()
);

RepositoryProvider gains exerciseProgress as its 13th member, and ActiveBenchmarkWorkout.vue goes back through the standard getter.

Move 2 — Rebrand the document model as adapter-neutral (avoid the 40-file trap)

The tempting-but-wrong move is inventing a parallel set of "clean domain types" and mapping at every boundary — a ~40-file refactor that adds a translation layer with no behavior. The audit shows the Db* types are already storage-agnostic plain TypeScript (discriminated unions, embedded arrays, nullable fields). They are your document model; only their name and address say "Dexie".

  • Declare schema.ts the canonical, adapter-neutral persisted document model shared by all adapters. Both Dexie and Jazz store these exact shapes (Jazz: blocks land in a s.json() column, scalars/refs become real columns).
  • Do the rename as a mechanical, zero-risk alias pass when convenient: Db* → Stored* (or re-export under new names and deprecate old ones). Ship it separately from any behavior change.
  • One real type-level task remains: the persisted-vs-domain conversion in converters.ts stays exactly where it is — above the adapters, below the UI. Adapters must not re-implement conversion.

Move 3 — Add the reactivity port (the one missing capability)

This is the structural gap. Define a minimal live-read contract on the interfaces — small enough that Dexie, Jazz, and the mock can all honor it:

// src/db/interfaces.ts
export interface LiveQuery<T> {
  /** Current snapshot; resolves immediately from local storage. */
  get(): Promise<T>;
  /** Fires with a fresh snapshot on every change, including remote/sync changes. */
  subscribe(onChange: (value: T) => void): () => void; // returns unsubscribe
}

export interface WorkoutsRepository {
  // existing one-shot methods stay …
  observeHistory(limit?: number): LiveQuery<DbCompletedWorkout[]>;
}

// src/composables/useLiveQuery.ts — the one Vue bridge, written once
export function useLiveQuery<T>(make: () => LiveQuery<T>) {
  const data = shallowRef<T>();
  let stop: (() => void) | undefined;
  onMounted(() => { const q = make(); q.get().then(v => (data.value = v));
                    stop = q.subscribe(v => (data.value = v)); });
  onUnmounted(() => stop?.());
  return { data };
}
  • Dexie adapter: implement with liveQuery() from Dexie itself — this also delivers the cross-tab reactivity your dexie-improvements.md Phase 2 wanted, so that plan is subsumed rather than duplicated.
  • Jazz adapter: implement with its subscription engine (what useAll uses internally) — remote sync updates flow through the same pipe for free.
  • Migration is incremental: convert composables one at a time (start with useRecentWorkouts, settings, active workout). One-shot methods remain valid for write-then-navigate flows.
  • Use shallowRef for the snapshots — consistent with the open perf note in repo-dexie-review.md.

Move 4 — Pin down intent semantics instead of transaction semantics

Your six ACID transactions are already hidden behind intent methods — the design is right, the contract is just implicit. Make it explicit in the interface docs so a CRDT adapter can implement honestly:

Also fold in the two open Dexie hygiene items while you're in these files: transactions around startFrom* if you decide they matter, and exists() via count().

Move 5 — Make tests adapter-agnostic (they are your swap insurance)

  • Replace the ~30 raw-db imports in integration tests with seed/assert helpers that go through repositories: dbAssertions.ts and benchmarkHelpers.ts already centralize much of this — finish the job so only those helpers may touch storage.
  • Then flip the whole integration suite into a contract test suite: run it once against Dexie (fake-indexeddb, as today) and once against any new adapter (Jazz memory driver: { type: "memory" }). Green suite on both = the adapter is certified. This is the strongest possible definition of "swappable".
05

Phased roadmap

Ordered so every phase ships value on its own, even if you never adopt Jazz. Phases 1–3 are pure hardening of the app you have; Jazz only enters at Phase 4. Effort assumes solo work alongside normal feature development.

PHASE 1

Close the seam

~2–3 days · no behavior change

After this phase, "which database?" is answered in exactly one file.

  • Add setRepositoryProvider() to provider.ts; select adapter in main.ts via VITE_DATA_BACKEND.
  • Fold exerciseProgress into RepositoryProvider; delete its special-case singleton and reset function.
  • Route ActiveBenchmarkWorkout.vue through getBenchmarksRepository().
  • Deduplicate generateId() (defined in both index.ts and database.ts) into one seam-level export.
  • Exit check: grep proves no production import of implementations/dexie outside src/db.
PHASE 2

Reactivity port

~1 week, incremental · immediate UX win

Live reads through the seam; Dexie's liveQuery backs them today, sync backs them tomorrow.

  • Add LiveQuery<T> + observe*() methods to the interfaces (start with workouts, settings, activeWorkout, templates, weight).
  • Implement in the Dexie adapter via liveQuery(); write the single useLiveQuery Vue bridge.
  • Convert composables opportunistically — each conversion deletes a manual-refresh call site and gains cross-tab updates.
  • This supersedes brain/reference/plans/dexie-improvements.md Phase 2 (mark it there).
PHASE 3

Contract test suite + type rebrand

~1 week · mostly mechanical

The integration suite becomes the certification harness for any adapter.

  • Purge raw db imports from tests; all storage access via repository-backed helpers.
  • Parametrize the suite over a provider factory (Dexie first; any future adapter plugs in).
  • Mechanical rename Db* → Stored* with temporary re-export aliases; move nothing, break nothing.
  • Document intent-level consistency guarantees (§04 Move 4 table) as TSDoc on the interfaces.
PHASE 4

Jazz spike (time-boxed, behind a flag)

~1–2 weeks, time-boxed · decision artifact, not production code

A worktree/branch spike answering the adoption question with numbers, not vibes.

  • Pin jazz-tools@alpha (2.0). Define the schema: real columns for ids/timestamps/refs, s.json() for block payloads, legacyId everywhere.
  • Implement createJazzRepositoryProvider() for 3 repositories first: workouts, settings, activeWorkout (the hot gym path).
  • Run the contract suite against it (memory driver in CI, OPFS in the browser).
  • Measure on a mid-range phone: bundle delta (WASM engine vs Dexie's ~tens of KB), cold-start to first render, set-logging write latency, 2k-workout history query.
  • Go/no-go gate: instant-input budget holds, contract suite green, bundle cost acceptable for a PWA.
PHASE 5

Migration & sync enablement

only after Jazz 2.0 ships stable · gated on Phase 4 “go”

One-way, verified, reversible-by-backup migration; sync as a user-visible opt-in.

  • Migrator = read via Dexie repositories → batched db.transaction inserts in dependency order → verify counts + spot-check hashes → flip VITE_DATA_BACKEND flag → keep Dexie data untouched as rollback for N releases.
  • Force a JSON export (existing v1 format) before migrating — the export file is the true safety net and stays adapter-neutral forever.
  • IDs: keep existing UUIDs as legacyId; soft references (benchmarkId, exerciseDefinitionId, progressionId) are remapped in one pass.
  • Sync = add serverUrl (Jazz Cloud or self-hosted) + auth upgrade path (local secret → passkey via Better Auth). Local-only remains the default — accounts stay optional, honoring the no-accounts principle.
  • Revisit exerciseProgress: today it full-scans workouts; with Jazz indexes, back it with an indexed query (or a small denormalized table — same fix Dexie's improvement plan proposed).
06

Decision log

ADR-01 · Proposed

Keep Dexie as the production engine; treat it as adapter #1, not legacy

Dexie stays the default until an alternative beats it on the app's own metrics.

It is small, synchronous-feeling, battle-tested in this app, and satisfies every current requirement. "Swappable" is about optionality, not about leaving. Rewriting the working engine before the seam is closed would be motion without progress.

ADR-02 · Proposed

Target the Jazz 2.0 relational model; ignore the 0.20 CoValue API

All interface design assumes a table/where/subscribe-shaped backend; no code is written against co.map().

0.20's load-graph-and-filter-in-memory querying doesn't scale to years of workout history, and the vendor's own docs have already moved to 2.0. Designing for 2.0 also keeps the interfaces isomorphic to Dexie — one contract, two honest implementations. The cost: waiting for 2.0 to leave alpha before Phase 5.

ADR-03 · Proposed

No parallel "clean domain model" layer

The existing persisted document types are declared adapter-neutral and renamed; no per-boundary mapping layer is introduced.

The types contain no Dexie constructs. A second model + mappers for ~40 files would add a permanent translation tax to every feature to fix what is only a naming problem. converters.ts (persisted ↔ runtime domain) already exists and remains the single conversion point.

ADR-04 · Proposed

Reactivity becomes part of the port, not a Dexie feature

Live reads are expressed as LiveQuery<T> on the repository interfaces; liveQuery() / Jazz subscriptions are hidden implementations.

If composables imported Dexie's liveQuery directly (the old improvement plan's approach), every converted composable would become new coupling to un-swap later. Putting subscription in the contract makes sync a backend detail — the UI can't tell a cross-tab update from a cross-device one. That is the whole point.

ADR-05 · Proposed

The contract test suite is the definition of "swappable"

An adapter is supported if and only if the shared integration suite passes against it.

Interfaces guarantee shape, not behavior. Only executable contracts catch semantic drift (ordering, null handling, intent atomicity). This also converts the existing raw-db test debt into the project's strongest asset.

07

Risks & mitigations

Jazz 2.0 API churn HIGH · external

Alpha software; DSL, permissions, and query surface are actively moving. Code written today needs maintenance before stable.

All Jazz code stays inside implementations/jazz/ behind the contract suite; churn is absorbed in one folder. Phase 5 is explicitly gated on a stable release.

WASM + OPFS footprint vs. "instant PWA in the gym" MEDIUM

Jazz 2.0 ships a Rust/WASM engine in a SharedWorker over OPFS — heavier download and cold-start than Dexie; OPFS needs a secure context and is shakier in some webviews.

Phase 4 measures exactly this on a mid-range phone before any commitment; the no-go path (stay on Dexie, keep the port) is a fully acceptable outcome that still delivers Phases 1–3's value.

Abstraction tax on daily feature work MEDIUM · self-inflicted

Over-generalizing the port ("support any conceivable database") would slow every feature down — the opposite of the app's north star.

The port's API is the union of what Dexie and Jazz 2.0 both do well, nothing more. No generic query builder, no capability flags. If a third backend ever demands more, extend then.

Migration data loss / broken references LOW likelihood · HIGH impact

Thousands of records with soft foreign keys (benchmarkId, progressionId, exerciseDefinitionId) must survive the move intact.

Forced JSON export first; legacyId columns preserve original identity; count + referential-integrity verification before the flag flips; Dexie data retained untouched for rollback across several releases.

Eventual consistency surprises after sync ships DEFERRED

Two devices completing/editing the same workout concurrently produce merge outcomes ACID never had to define.

Intent-level semantics documented now (Move 4) so every adapter implements a stated contract; embedded-document model means most merges are whole-document and naturally conflict-free. Full conflict UX is a Phase 5 concern, deliberately out of scope today.
